## 1. The bug we investigated

**Source:** the admin log `C:\Users\Pulkit\OneDrive\Desktop\stakbridge-log_2026-11-13_1529.csv`.

**The user's report:** trades were open on the master and copied to the clients. The master never closed them, but the clients' copies were closed anyway.

**What happened (13 Nov, 07:13:29):**
1. The master account `acct_e2bec70a` lost its MetaTrader 5 broker authorization. MT5 logged "Authorization failed" and logged in again.
2. While it was logging in again, MT5's `positions_get()` returned an empty list and reported no error (`last_error` = RES_S_OK).
3. The master worker (`stakbridge/workers/process.py`) reads twice to be safe, but both reads were empty. It sent one diff that said **all 50 master trades were closed**.
4. The copier closed every copy on all 8 clients. Each close came later than the one before it (about +300 ms per close per client), because each client sends its orders one at a time.
5. The master reconnected at 07:13:40. The 33 tickets that had been forgotten weren't in the "seen" list, so they were marked **"too old to copy"**. Their database rows were also overwritten with status `skipped` / `TOO_OLD_AFTER_RESTART`, because `db.save_copies` uses ON CONFLICT DO UPDATE. That erased their close history from the Trades pop-up. The other 17 tickets still had rows in memory.
6. The same LOGIN_FAILED had happened on 8 Nov and 10 Nov without doing damage, because no trades were open those times.

## 2. The fix (implemented on main, uncommitted)

The rule now is that a master trade counts as closed only when MetaTrader's own history shows the close.

| File | Change |
|---|---|
| `stakbridge/workers/backends.py` | New `Mt5Backend.confirm_gone(items)`. It returns `None` if the terminal is not connected, if `terminal_info`/`account_info` is None, or if the login is wrong. Otherwise it returns one True/False per ticket: positions are checked with `history_deals_get(position=)` for a deal with entry OUT/INOUT/OUT_BY, and pending orders with `history_orders_get(ticket=)`. FakeBackend gained a `history` set, a `glitching` flag and `glitch(on)`, which makes `snapshot()` return `{}`. The fake `confirm_gone` returns `{t: t in history}`, or None when offline. Every fake close, cancel or fill now records history. |
| `stakbridge/workers/process.py` | `CONFIRM_GONE_SECONDS = 30`. `_watch` sends tickets missing from a read through `_held_back`. A ticket is released as closed only once `confirm_gone` confirms it; otherwise it is held and stays "open". On the first hold it logs one warning: "...no longer shown, but ... (MetaTrader logging in again?): not treated as closed, client copies stay open". There is a fallback: after 30 s with a *healthy* terminal and no history close, the ticket is treated as closed anyway, so a real close is never lost. Tickets that reappear are un-held and logged. New worker commands are `glitch` (fake backend only) and `confirm_gone`. Workers can now send `{"event":"log"}` messages. |
| `stakbridge/workers/manager.py` | Handles the new `event == "log"` from workers and writes it to the app log with the account. |
| `stakbridge/copier.py` | New `_unsure` dict, plus `_asking_gone` and `_log_when_gone`. **After a reconnect**, copies of master trades missing from the first snapshot (baseline) stay open while the copier asks the master's `confirm_gone`. They close only when history confirms the close or the trade reappears; the fallback is 30 s. Guards in `_follow_master` and `_check_copy` stop the 1-second copy check from closing "unsure" copies. **"Too old" fix:** the new `_too_old()` first calls `db.copied_master_tickets`. If a trade was copied before, it logs "copied before: its client copies are left as they are, not copied again" and does not overwrite the rows. |
| `stakbridge/db.py` | New `copied_master_tickets(master_id, tickets) -> set[int]`, which looks tickets up in chunks of 500. |
| `tests/test_master_relogin.py` (new) | 5 tests: the master shows no trades for a moment and nothing is closed; a real close during a glitch is still followed; a reconnect with an empty baseline keeps the copies; a trade closed while disconnected is closed after the reconnect; a trade copied before is not marked too old. 3 of them fail on the old behaviour, so they really catch the bug. |

The memory note `stakbridge-copier-progress.md` has a "2026-11-13 FALSE MASS CLOSE" entry as well.

## 3. Test results

- **Full suite:** 388 passed. Run with `.venv/Scripts/python.exe -m pytest`. `tests/superadmin/test_exe_builder.py::test_built_settings_contain_server_url_and_no_secrets` fails on the unmodified code too (checked with git stash), so it is not caused by today's work.
- The warning about an invalid `\s` escape (DeprecationWarning) in `process.py` was already there; I left it alone.

### Backend stress (`tools/memtest/stress_backend.py`, fake broker)
- **Setup:** 1 master and 8 clients, 40 rounds × 20 trades = **6,400 copies**, and **14 master glitches** (the master shows no trades for 1.5 s). Three threads called the page's API at full speed the whole time.
- **Client copies wrongly closed during glitches: 0.**
- **Latency (quiet benchmark, 6 clients × 40 trades, old code vs new code, 2 runs each):**

  | | Old | New |
  |---|---|---|
  | Open, median | 2.9 / 3.2 ms | 2.9 / 3.5 ms |
  | Close, median | 1.2 / 1.3 ms | 1.4 / 1.2 ms |

  The differences are noise, so latency is unchanged.
- **Memory:** the workers stayed flat at about 42 MB. The main process went from 52.5 to about 68 MB and then levelled off; the old code did the same (52.5 → 67.6).
- **Nothing builds up:** at the end, every copier state dict (including `_unsure` and `_log_when_gone`) and the store queue were empty.
- **API speed was the same on old and new code:** `/orders` median about 340 ms and `/accounts` about 35–39 ms, under heavy load.

### Live app (`tools/memtest/live_app.py`, the real app with the fake broker)
- It ran 439 cycles (about 38 min). All 200 recent orders were correct: closed ones closed on all 8 clients, open ones open on all 8.

### Frontend (`tools/memtest/ui_stress.py`, Edge driven through CDP)
- **Memory is flat on every tab:**

  | Tab | Memory |
  |---|---|
  | Accounts | ~32 MB |
  | Copier | ~55 MB |
  | Log | 72–80 MB |
  | Trades with the pop-up open, 20 min | levels off at 80–86 MB |
  | All tabs, 20 min | 72 → 84 MB |

  The JS heap stayed at about 2 MB and the listener count at 44.
- **Watch out:** CDP `Network.enable` makes Edge keep every response body. That looked like a leak (140 → 520 MB) but was caused by the test tool. The script now disables it unless `KEEP_NETWORK=1`.
- **Responsiveness:** in 20 min there were 5 long tasks (the longest 124 ms) and the worst freeze was 181 ms. Tab clicks had a median of about 20 ms, a p90 of 140–220 ms and a max of about 450 ms, with the refresh sped up and two browsers running.
- **Limit:** the CPU was shared, so the 20-minute runs only did about 2,400 redraws (roughly 40 min of normal use).
